renovate-adoption-review — design¶

Status: draft for review · Date: 2026-11-07

Problem¶

Renovate keeps dependencies current, but a version bump only changes the version. The consumer repository keeps its old workarounds, deprecated inputs and verbose configuration even when the new version offers a documented, simpler path. Nobody reads the release notes of every bump with the consumer's code in mind.

Goal¶

A portable skill that reads a dependency update (library, GitHub Action, Docker base image, build tool) and finds grounded opportunities in the consumer repository to adopt what the new version brings: replace deprecated APIs or inputs, drop workarounds the new version makes unnecessary, adopt new options that simplify existing configuration. It applies them in a reviewable change that explains what was applied and why, with a cited source for every change.

Success: on a real major update the skill either says "nothing to adopt" with reasons, or produces a change whose every item cites a release note, diff hunk or observed warning, and whose consumer checks pass.

Non-goals¶

  • Breaking-change risk review or fixing builds broken by an update (covered by existing tools; see Prior art).
  • Editing the Renovate configuration, adding dependencies, or changing a library's public API.
  • Editing files generated by the ci-kit Copier template (flagged only).
  • CI-triggered or scheduled execution in v1.

Prior art¶

No existing tool proactively proposes adoption of new features and delivers it as a stacked change on the update branch (web search, 2026-11; negative result, not proof). Closest: risk-only review skills and prompts for Renovate PRs (for example a review-renovate skill that checks pinned SHAs and removed action inputs), claude-code-action setups that comment on breaking changes, agents that push fix commits when a bump breaks the build, and deterministic migration recipes (OpenRewrite, Codemod) without Renovate integration.

Decisions¶

Topic Decision
Delivery for open updates Child PR stacked on the Renovate branch
Which open updates Majors, plus packages on a per-repository allowlist
Already-merged updates Batch retro mode producing one issue per run; optional apply
Target Consumer-owned code; ci-kit-generated files are flagged as "belongs in ci-kit"
Trigger Manual invocation (Claude Code, Codex, other runtimes)
Shape SKILL.md + deterministic POSIX shell helper over gh + per-ecosystem references
Location skills/repository/renovate-adoption-review/

Modes¶

Mode 1 — review <pr> (open update, before merge)¶

  1. Helper inspect <pr> returns a verdict: candidate or skip:<reason>.
  2. For a candidate: gather sources, find opportunities, apply, verify.
  3. If checks pass and at least one change applies: create child branch, open child PR into the Renovate branch, comment on the parent PR linking the child.
  4. If nothing applies or checks fail: no PR; post a report comment on the parent PR (applied nothing, considered items, reasons).

sweep lists the repository's open Renovate PRs with their verdicts so the user picks candidates; it changes nothing.

Mode 2 — retro (already merged, batch)¶

  1. Range selection: --since <date|tag|sha> or --last <N>.
  2. Helper retro collects merged updates: merged PRs authored by renovate[bot] with the dependencies label (Renovate on GitHub always merges through a PR, so no git log fallback).
  3. Aggregation: multiple bumps of the same dependency collapse into one interval from the earliest old version to the latest new version.
  4. Triage is wider than mode 1: majors and minors are candidates; digest, patch, pin and lock-file updates are skipped unless the package is allowlisted.
  5. Output: one GitHub issue per run (format below).
  6. With --apply: branch from the default branch, implement the findings, verify, open one PR to the default branch with Closes #<issue>. Findings whose checks fail are reverted and stay unchecked in the issue with the reason.

Components¶

scripts/renovate_adoption.sh (deterministic, POSIX sh, needs gh and jq)¶

  • inspect <pr> → JSON: {pr, branch, headSha, updates:[{package, sourceUrl, from, to, updateType, releaseNotesUrls}], verdict, reason}. Update type is computed from the from/to versions; the Renovate PR body table and labels are used only for parsing. Grouped PRs yield several updates; any non-skipped update makes the PR a candidate.
  • sweep → JSON array of inspect results for open Renovate PRs.
  • retro --since <ref> | --last <N> → JSON array of aggregated intervals with the list of source PRs/commits and a verdict per interval.
  • owned-paths → JSON array of consumer-relative template-owned paths, matched exactly (R7/R9; see Guardrails).
  • Allowlist: optional .github/renovate-adoption.json in the consumer ({"allow": ["actions/setup-java", "gradle"]}); absent file means empty list.
  • Exit codes: 0 success, 2 usage error, 3 gh/network failure (message on stderr, never a silent empty result).

SKILL.md¶

Trigger description, the two modes, the step order, grounding rules, guardrails, child PR mechanics, output templates, and stop conditions.

references/¶

  • ecosystems/github-actions.md — new or removed inputs and outputs, runtime (node) changes, changed defaults, SHA-vs-tag pin, composite action changes.
  • ecosystems/docker.md — base image variants, EOL notices, new tags, healthcheck and user defaults.
  • ecosystems/gradle-maven.md — deprecations via --warning-mode all, plugin DSL changes, toolchains.
  • ecosystems/npm-typescript.md, ecosystems/python.md — deprecated APIs, config keys, new built-ins replacing helpers.
  • templates.md — child PR body, parent comment, retro issue, retro PR.
  • stacked-pr.md — branch naming, drift handling, merge order, recovery.

Sources and grounding¶

Sources in order of trust:

  1. Renovate PR body (release notes it already fetched, compare link).
  2. GitHub Releases and CHANGELOG between the two versions (gh api).
  3. Tag-to-tag diff of the dependency narrowed to action.yml, public API, Dockerfile, migration documents (UPGRADING, MIGRATION).
  4. Local signals after the bump: build and linter deprecation warnings (gradle --warning-mode all, actionlint, hadolint, ruff, tsc).

Rules:

  • Every applied change cites a source: release-note URL or quote, diff hunk, or observed warning text.
  • A finding without a citation goes to "Considered, not applied".
  • A finding without confirmed usage in the consumer (located by search) is dropped.

Guardrails¶

Allowed: replace a deprecated API, input or option with its documented successor; remove a workaround the new version makes unnecessary; adopt a new option that simplifies existing configuration; update comments and docs naming the old version.

Forbidden: new dependencies; public API changes of the consumer library; edits to Renovate configuration; edits to ci-kit-generated files (helper owned-paths reads _src_path and _commit from every .copier-answers*.yml, lists the template tree at that commit, keeps blobs under the template's _subdirectory (read from its copier.yml, with {{ var }} rendered from that answers file), strips that prefix and the templates suffix (default .jinja), and treats a consumer path as owned when it equals one of the results; reported under "Belongs in ci-kit"); unrelated refactors; weakening or deleting tests.

Size: a finding touching more than 10 files is proposed, not applied.

Verification: run the consumer's own checks (build, lint, tests as documented in the repository). A failing finding is reverted and reported; the skill never claims success without a passing run.

Child PR mechanics (mode 1)¶

  • Branch name adopt/<renovate-branch-without-prefix>, never under Renovate's branchPrefix: Renovate prunes its own branches it considers stale (pruneStaleBranches).
  • Nothing is pushed to the Renovate branch while the child is open, so Renovate keeps rebasing it. Merging the child makes the branch "modified" and Renovate stops committing to it; merging the parent is the next step anyway. gitIgnoredAuthors is not required in v1.
  • The child PR body carries a hidden marker <!-- adoption-base: <sha> --> with the parent head SHA at creation.
  • Re-running review <pr> on a parent whose head moved: git rebase --onto <new-head> <old-head>, re-run checks, git push --force-with-lease, update the marker.
  • Merge order, stated in both PRs: child into parent, then parent into default.
  • Parent merged or closed first (including Renovate autoclosing a superseded parent and deleting its branch): re-running retargets the child to the default branch (gh pr edit --base) and rebases it; if GitHub already closed the child, the skill opens a new PR from the same branch and links the old one.

Output formats¶

Child PR / retro PR body:

  • Update: package old → new (type) with release links.
  • Applied: per change: what, why, source citation.
  • Belongs in ci-kit: template-owned opportunities with citations.
  • Considered, not applied: item and reason.
  • Verification: commands run and results.
  • Risk: low / medium with one line.
  • Marker (mode 1 only).

Retro issue: title Adoption review: <range>; one section per dependency interval with the source PRs, findings as a checklist (each with citation, consumer locations, proposed change, risk), and a "Belongs in ci-kit" section.

Error handling¶

  • gh or network failure: stop and report the failing command; no partial PR.
  • Release notes unavailable: fall back to the next source; if none, report "no sources" and skip the dependency.
  • Dirty working tree or wrong branch: stop before any edit.
  • Child branch already exists: reuse it via the drift path, never create a duplicate.

Testing¶

  • Helper: Python tests in tests/ (matching the hub's existing script tests) that run the script against recorded gh JSON fixtures through a stub gh on PATH: major PR → candidate; digest → skip; grouped PR with one major → candidate; allowlisted minor → candidate; retro batch with repeated bumps → one aggregated interval; gh failure → exit 3.
  • Hub validation: ./scripts/validate.sh --full.
  • End-to-end canary: one real open major in a quokkify repository (for example the open classgraph major in archgate or q4j) in mode 1, and one retro run over the last month of merged updates in a repository consuming GitHub Actions updates.

Later (not v1)¶

  • Headless CI execution reusing the helper (claude-code-action).
  • Separate ci-kit issue or PR for "Belongs in ci-kit" findings.
  • Dependabot PR parsing.
